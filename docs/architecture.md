# Randpic 2.0.0 架构

## 模块职责

| 模块 | 职责 |
| --- | --- |
| `__init__.py` | 插件元信息、配置、启动关闭钩子和网页路由注册 |
| `handlers.py` | NoneBot 匹配规则、权限、消息回执和命令交互 |
| `service.py` | 异步入口、操作锁、线程调度、下载、发布和后台重试 |
| `library.py` | 启动核对、文件命名、图片添加、抽取和引用删除 |
| `repository.py` | SQLite 初始化、事务、加权抽取、历史引用和同步任务 |
| `journal.py` | 文件操作日志、暂存备份、提交后清理及失败恢复 |
| `compress.py` | 图片验证、压缩、真实格式和感知哈希 |
| `web.py` | 分页 HTML、本地副本、远端发布清单 |
| `ali_oss.py` | 复用 OSS 异步客户端、上传／删除与超时 |
| `config.py` / `utils.py` | 配置读写、路径与命名、原子写入、跨进程互斥 |

## 图片身份与发送次数

`randpic_images` 中一张图片有独立 UUID；文件名用于磁盘访问，UUID 用于消息引用。目录和文件重命名后，可通过内容 SHA-256 找回原来的图片身份。原路径被新内容替换时会生成新的 UUID，原图片标记为删除。

`randpic_messages` 保存 `(bot_id, group_id, message_id) → image_id`。随机发图和添加成功的图片回执都会保存对应关系。删除后的图片记录作为历史标记保留，因此重复删除可返回“已删除”，也不会影响后来添加的图片。

发送次数只在随机图片的发送接口成功返回后累加；添加图片时的回执不增加次数。发送成功但进程恰好在记录前退出，可能漏记这一次，QQ 消息发送和 SQLite 提交无法组成同一个事务。

### 数据库加权随机

对于分类中每张有效图片，定义 `w = 1 / (send_count + 1)`。SQLite 通过窗口函数计算累计权重，用一次随机数乘总权重，选择累计权重首次达到该随机位置的图片。

因此图片被选中的概率是 `w / sum(w)`。例如次数为 0 和 9 的两张图片，概率约为 10:1；这不是严格轮询，仍然可能连续发送同一张图。

抽取只把最终一条图片记录传给 Python。Python 不读取所有候选图，也不建立权重列表；SQLite 仍须扫描该分类并计算窗口结果，数据库内部可能使用排序及临时存储，这不是数据库层面的常数空间或常数时间算法。

## 文件与数据库的一致性

压缩和校验完成后，新增内容先写入内部准备目录。真正修改文件前，写入文件操作日志；重命名或删除原图时保留同目录备份。接着在 SQLite 事务中修改图片记录、编号和内容修订号。

- 数据库提交成功：清理日志和临时备份。
- 事务失败：恢复原文件、撤销本次安装的目标文件。
- 操作中断：下次启动先根据数据库中的图片身份及状态恢复日志，再扫描图库。
- 恢复位置被其他程序占用：记录错误并保留备份，避免覆盖未知文件。

同一服务实例内的文件和数据库修改由异步锁串行安排；实际 CPU 和磁盘操作在线程中完成。跨进程锁防止两个 Bot 进程同时维护同一目录。任务被取消时，等待已经进入线程的修改结束后再释放锁。

文件系统与 SQLite 之间不存在真正的跨系统原子事务。恢复日志降低中断损坏风险，不能替代磁盘故障后的完整备份。

## 启动核对

启动只扫描 JSON 中已配置的指令目录：校验图片、识别真实格式、必要时压缩并整理命名，再按路径和内容匹配已有身份。已经规范的文件不会每次启动重命名；不同后缀不允许共用主文件名。新编号大于磁盘和数据库记录中的已有最大编号。

离线新增的图片从 0 次开始；原图的内容和身份可以匹配时保留发送次数。离线移除的图片标记为删除。损坏图片保留在磁盘并输出错误，不纳入可发送图库。JSON 格式损坏时保留原文件，不覆盖用户配置。

## 网页和 OSS

本地 `public` 是可重新生成的发布目录，按数据库当前内容复制图片并生成分页和分类首页。写入单个文件时使用临时文件替换；增删后移除过期页面及图片副本。页面为纯静态 HTML，浏览器手动刷新即可查看最新内容。

OSS 有独立的发布清单，排除配置指定的分类。清单与已知远端对象比较后生成持久化任务，后台并发上传／删除。网络请求期间不占用图库操作锁。任务带有递增版本号：旧上传结束时只能确认自己的任务，不能清除同时产生的新删除任务。

失败任务约每 30 秒重试，重启后继续处理。远端图片和页面按阶段处理；各对象并非一次原子发布，故障时可能出现短暂不同步。`上传oss` 可以重新发布所有当前对象。发布目录为本插件专用，不应放入需要保留的手工文件。

## 首次初始化与后续启动

数据库不存在时直接创建当前结构，随后扫描配置的图片目录，校验和整理实际文件，为每张图片建立 UUID、内容哈希、感知哈希等索引，发送次数初始为 0。

后续启动会使用已有数据库核对文件变化，保留匹配图片的 UUID、发送次数、消息引用和同步状态。`randpic_meta` 保存当前数据库结构版本，以及服务端内容修订号和发布进度，用于结构检查及增量发布。

图片文件可以重建图片索引，但无法恢复发送次数、历史消息引用及远端任务状态；删除数据库相当于清空这些运行数据。
